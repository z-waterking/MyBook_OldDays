# 《vibe coding带来的虚无感》评价

> 复评日期：2026-09-06。以归档原文为对象，按文体目的、结构、语言、人物与主题综合评定。

## 总体印象

文章最有价值的矛盾是：作者越熟练地使用AI，越难确认自己的不可替代性。学习编程的时间成本，与几天攒出系统、展示时却改不了代码的现场形成反差，使“虚无感”有明确来源。前半部是一篇可信的职业经验随笔，后半部逐步转为关于软件、就业、消费与脑机接口的未来推演；问题越问越大，文本的证据却没有同步增加。

## 亮点分析

**成功现场反而暴露失控。** 角落里的电脑、不断修补的小问题和括号里的自揭短，比反复说“焦虑”更具体。系统已经做出来，作者仍无法亲手维护，成果与能力发生分离。

**学习史让手艺贬值可感。** 流程图、C语言、项目和编程题不是单纯履历，而是为后来“古法编程”的命名提供时间重量。

**训练新员工的类比贴近经验。** 告诉AI读什么、错了怎么办、什么时候来问，与带实习生的流程对应，能让非程序员理解工作的变化。作者同时承认上瘾和不安，立场因此比单向赞美或反对更复杂。

## 写作建议

1. 把“做得更快”“自己能否判断”“岗位是否减少”分开讨论。效率变化在文中有亲历支持，全行业岗位和消费后果则需要额外论证，不能靠“必然”把推测连成事实。
2. 末段软件消失、考试消失与脑机植入同时出现，削弱了前文最独特的经验。可保留一个真正追问到底的问题，例如展示现场自己究竟还能负责什么。
3. “普通人难以操作”与“换个人也能做”之间有值得展开的张力。补一件真实发生过的需求判断、验收或失败，能检验作者的担心；不必预设人一定更强，也不必预设人已经没有价值。
4. 修正工具名、拼写和“经历／精力”等文字问题，并注明技术体验对应的时间。结尾若回到那台展示用电脑，比继续扩大预言范围更能留住读者。

## 金句摘录

1. “以前那种自己琢磨代码，瞬间成了“古法编程”，早不知道扫到哪个垃圾堆里面去了。”——“古法”的怀旧意味被后半句猛然打断，写出技能价值的骤降感。
2. “由于太快了，我没有看过里面的代码，所有的修改都是让copilot github来完成的。”——“太快”从优点变成无法掌控的原因，经验内部就有反讽。
3. “相应的，我们对代码的控制权在减弱。”——短句将工具方便与个人代价接在一起，是前半部的关键转折。
4. “整个流程，妥妥就是带实习生上手项目的过程。”——用熟悉的劳动关系解释新工具，口语感也保持了作者声调。

## 综合评分

**7.8/10**

在技术劳动随笔中，本篇的第一人称现场和矛盾意识较突出；与《我在阿里的最后一个leader》相比，它更能反观自己的能力和选择。但相较《工位》，后半部缺少能承载情绪的具体场景。7.8分体现经验部分的质量，也反映论证跨度、重复设问与绝对判断对整篇造成的损耗。

## 综合评价

这篇已经抓住一个值得保存的职业时刻：产出增加时，自我价值未必随之增加。最需要编辑的是从个人体验走向社会结论的接缝。守住自己实际看见、实际做过的事情，文章反而会更有长期价值。
