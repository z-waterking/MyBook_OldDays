# vibe coding带来的虚无感

最近用 AI 写代码，最让我心虚的一次，是出去展示自己做的项目。

系统是我攒的，电脑也是我提溜过去的。出了小 bug，我就躲在角落里，让 AI 帮忙改。

因为我自己改不了。

## 古法编程

最早接触编程，是高中画流程图。大学学 C 语言，写个循环，从 1 加到 100，也就差不多了。那时候没觉得几个循环能拼出什么东西，课程也没学成体系。

研究生转到计算机专业，又去广州的游戏公司干过活，才算摸到了门。此后翻书、手写代码、做项目、刷题，折腾了许久，终于能比较顺手地写程序。

工作的前两年，AI 主要帮忙补全代码。碰上不会的，还是得自己找资料，去 GitHub 上找别人的实现，复制下来研究。复制也是有门槛的，总得知道它该放哪儿，为什么不跑。

这两年，事情变了。你把想要的功能告诉 AI，它直接给你做。以前自己琢磨代码的那套，忽然有了一个很讲究的名字：古法编程。

多年练成一门手艺，还没怎么传给后辈，先成非遗了。

俺们公司刚推 GitHub Copilot 时，我拿它试了以前颇费工夫的爬虫。搭框架、解析网页、处理 IP 池、把内容存到本地，原先要分头查资料的事情，它一次就能给出一套代码。生成的东西仍然要试，但查找和拼装的工夫确实省了。

然后就到了去年的 hackathon。

## 系统做出来了

我熟悉算法和数据，前后端没那么熟。偏偏要做一个前后端都有的系统，还只有我一个人写。

那就让 Copilot 上。我描述架构，让它实现，拿到本机测试；出了 bug，再贴回去让它修。循环了几天，系统就攒出来了。

快是真的快。快到我没有认真看过里面的代码，后续修改也全交给了它。后来有机会出去展示，我才发现，项目能跑和我能维护，是两码事。

于是就有了开头那一幕。我带着做好的东西出门，守在角落里，等 AI 把它修好。展示机会到手了，古法编程也没能救我，毕竟我连这套代码都没看过。

再后来，公司允许用 Claude Code。我的日常变成了让它写代码，再让 Copilot 帮忙 review。新模型出来就试，哪个顺手用哪个。

不用一行行翻日志，不懂的直接问，想改的直接说。看着代码不断往外冒，运行起来还真能用，正向激励给得足足的，很难不上瘾。

但任务做得越快，我越容易冒出一句：这个事情换个人是不是也能做？那么，给我发工资的意义是什么？

## 带一位新员工

最近搭了一套 harness，把项目说明、操作规矩和检查步骤整理给 AI。搭到一半我才反应过来：这不就是带实习生吗？

先看哪些文件，从哪里入手，不能做什么，做错了怎么补，什么时候必须回来问我。一项一项交代完，新员工就开始干活了。

想同时多做点事，目前最直接的办法就是再开一个对话窗口。不仅能做熟悉的领域，还能伸手去做原先不会的东西。这种能力以前要花很长时间才长得出来，现在开个窗口就有了，至少看起来有了。

可我也发现，不熟悉项目的人未必能顺利用好这些工具。需求没讲清，结果不会验，AI 可以陪着你来回改很久。身边有些人盼着它成为全自动助理，回消息、发邮件、修电脑，一声令下全办妥。按我目前用下来的情况，还得有人守着。

这又跟我的担心拧在一起了：我一边觉得自己随时能被替换，一边又知道，不是把窗口交给另一个人，事情就一定做得成。

眼下要想清楚的，也许就是我守在这里，到底守的是什么。哪些结果我能判断，哪些只是见它没报错，就当作对了。

至于以后会少掉多少岗位，软件会变成什么样，我当然也担心。省出来的人力最后去了哪里，收入少了，谁来买那些更便宜、更快生产出来的东西？这些问题不会因为我多开几个窗口就有答案。

这篇写着写着，已经从代码想到全行业失业，又想到人类去给机房降温。想得挺远，展示时那个小 bug，却还是得靠 AI。

那台展示用的小破电脑倒很诚实。它不讨论人类的未来。系统出了问题，先等我处理。

我再去等 AI。
